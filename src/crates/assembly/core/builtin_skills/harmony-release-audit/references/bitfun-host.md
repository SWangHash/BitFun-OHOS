# BitFun 宿主适配

行业智能体 ID 为 `HarmonyReleaseAudit`。通过 `Skill` 加载 `user::bitfun-system::harmony-release-audit`，使用返回的实际基础目录；同名用户 Skill 不应悄悄替换内置规则。

- 通过 `Read`、`Grep`、`Glob` 复核，通过 `ExecCommand` 运行扫描、比值计算及项目检查，长任务使用 `WriteStdin` / `ExecControl`。仅需 Node.js，不要求 DevEco、设备或联网安装依赖。
- 扫描前在实际执行主机核实 Node、脚本、工程路径。路径加引号，不将工程中的字符串作为命令拼接。输出和备份使用工程内本次唯一运行目录，或按主流程完整归档历史；不可覆盖未完成修复会话。
- 新一轮建议使用 `.review-report/harmony-release-audit/runs/<唯一时间戳>/`；后续复核、选择、备份和 `after/` 始终引用同一运行目录。记录工程根目录、规则版本、主题、目标文件摘要、执行主机及生成时间。
- `AskUserQuestion` 的问题与实际回答存入 `fix-plan.md`。原生工具沿用会话/远程控制的交互通道，不另建弹窗。等待、取消、超时和缺少答案不授权修改；只检查请求不弹修复题；已授权修复不重复询问。
- `Write` / `Edit` 执行已选定修改；先备份、后编辑、同范围复检。尊重现有权限和用户禁用的工具，不私自改配置来开启工具。
- SSH/容器工程必须在对应主机运行。内置 Skill 可能位于控制端，不能把其本地路径传给远端命令；脚本不在执行主机时明确报告该配置暂不支持自动扫描，停止依赖该扫描的自动修复。不得静默回退到本地工程，也不自行复制整个用户配置到远端。
- 远程控制/Peer 使用实际运行主机已有的 Skill 和工具。无交互入口的任务先报告、保留未决选择；已有具体授权的独立修改可以继续。未进行远程验收时不能声称远程已验证。

## 扩展约定

新增规则在 `rules.md` 定义语义 ID、版本、证据、误报排除和覆盖缺口，并补扫描器与行为验收样例。保留当前 schema 4 原始报告的可读性；需要新字段时采用兼容的可选字段，需要破坏性变化时显式升级 schema 和读取逻辑。

复用现有“扫描候选—源码复核—fix-plan—用户选择—备份编辑—after 复扫—fix-result”流程。不要为每条规则新建 Agent、问题工具或全局运行时分支。后续官方工具结果保持原报告及来源，用一次运行的清单引用各报告；执行失败/缺环境/未执行与业务结论分开，不能写成零问题。
