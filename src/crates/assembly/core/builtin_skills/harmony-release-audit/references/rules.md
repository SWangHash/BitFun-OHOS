# 手机源码规则与证据边界

版本：`phone-source-mvp-0.4`。审核基线来源为用户提供的色彩对比度、发布完整性和隐私主动同意要求；未将其宣称为已联网核验的最新官方版本。若用户提供后续正式规则，应核对并更新此文件和对应测试。报告使用“按本次规则确认风险”，不能据此声称商店必定拒绝或完整审核通过。源码和产物只使用本文件的语义标识与中文名称，不记录外部审核规则序号。

只检查手机候选源码。模块入口来自工程注册的 phone `entry/feature`，再沿 `oh-package.json5` 中本地 `dependencies`、`dynamicDependencies` 递归纳入依赖源码。被入口直接或间接依赖的 HAR 不因自己的 `deviceTypes` 缺少 phone 而排除；该声明冲突写入 `scopeNotes`。动态依赖的实际加载仍需复核。与手机依赖图无关的模块排除，元数据缺失/损坏的候选范围保守处理并报告。

`moduleScope` 记录每个模块是否纳入、原因和直接依赖方；`scopeNotes` 记录设备声明冲突、未解析本地依赖和入口不明等范围问题。手机入口依赖纳入不等于当前产品构建或所有页面必然可达，Agent 仍核实构建条件、引用与路由。外部 SDK、工程外源码、归档依赖、生成代码、二进制、图片内文字不在自动源码覆盖范围；不能用“诊断 0 条”掩盖这些缺口。

## 色彩对比度（color-contrast）

用户基线：图标/标题 `> 3:1`，正文 `> 4.5:1`。等于边界不通过；使用完整精度比较。W3C 的 [sRGB 相对亮度和比值公式](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum)仅用于计算，不替换用户给出的严格比较运算和文字角色定义。

本预检按下表统一文字角色。它是对用户基线的工程判定口径，不宣称替代官方完整的字号/角色细则：

| 文字用途 | 本预检角色与阈值 | 复核依据 |
| --- | --- | --- |
| 引出页面或内容分区的标题、副标题 | 标题，`> 3:1` | 文字实际承担内容层级和命名作用，结合布局、文案、使用位置确认 |
| 说明、协议、价格、合计金额、订单状态、促销标签、按钮、菜单和导航文字 | 普通功能文字，按正文 `> 4.5:1` | 显示数据、状态或提供操作；同类用途采用相同口径 |
| 文案或用途无法追踪 | 角色待核实 | 说明缺失的调用/数据证据，不仅写“待产品确认” |

较大字号的金额不自动成为标题；信息重要程度不改变阈值。反过来，小字号也不能单独证明正文身份。已从源码确认是按钮、标签或状态等用途后，按表判定，无需把它们反复保留为“可能是标题”。明确有证据承担标题作用的组件可按标题处理，报告中写出证据。

- 自动分析 `Text` 组件修饰链，选择最后一次颜色赋值，沿同一文件中的容器层级寻找背景，不跨兄弟组件取色。
- 支持明确的颜色字面量、少量固定 Color 枚举、`$r('app.color.name')`、`$color:name` 别名，以及前景/背景透明度在已知背景上的合成。ARGB 八位颜色按 `#AARRGGBB` 解析。
- 资源先按当前模块、已声明的本地依赖层级、AppScope 查找；同层依赖冲突不猜测。此模型不替代最终构建的资源合并规则，产品特定覆盖需额外核对。
- 分开处理 base/dark；其他限定词、未知别名、缺失资源、损坏文件不判通过。
- Stack/重叠、自定义组件背景、图片/渐变、视觉效果、动态表达式及需要展开的自定义样式记录为缺口。源码词法模型无法解析全部 ArkUI 语法或跨组件传参。
- `ratio <= 3` 表示已计算的颜色组合未超过两类阈值；`3 < ratio <= 4.5` 需确认正文/标题身份。字号只是辅助证据。所有静态结果还需确认实际显示路径。
- 原始 `contrastChecks` 的 `resolvedForeground`、`resolvedBackground`、`compositedForeground` 保存实际参与计算的颜色，资源/组件证据仍见 `foreground`、`background`。修复建议使用 `--contrast` 在实际最终背景上重算，保留输出的输入颜色对和完整比值；不要把白底测算值复制到浅灰底。透明背景须先追踪到底层不透明颜色。
- 未提供 dark 资源本身不等于存在深色模式缺陷；显式颜色在两种资源选择下相同，也不证明系统默认文字、主题配置和最终渲染相同。检查应用色彩模式设置与系统主题后，仍依赖运行时的列为待实测。
- 本版不自动计算 Image/SymbolGlyph 等图标及富文本每个 Span 的最终颜色；单独报告覆盖范围，不把它们默认为合格。

## 发布完整性（release-readiness）

- 自动检查应用名称/包名、组件直接文案和被引用的字符串资源，保留资源语言、引用组件与行号。
- `test/demo/beta/vConsole/内测/测试` 只产生候选；发布入口、业务语义和构建条件决定是否构成问题。
- 注释、日志、依赖名和未使用资源中的词语不直接构成用户可见测试版本证据；`contest/latest` 等普通单词不应因为子串误报。
- AppScope 标签与 Ability 标签可能不同，应分别核对。动态图像文字、数组/变量拼接、远程文案、条件编译不能靠本版脚本穷尽。
- 未完成功能/测试模块必须给出正式页面入口、具体空实现或不可用路径；只有 TODO 字样只能提醒进一步检查。
- 用户可见的功能菜单无匹配事件分支、业务操作只返回上一页等情况，先追踪实际处理链；仅缺少内联 onClick 不证明空实现。若入口与空实现都可证明，作为“发布完整性”的人工补充风险单列；发布条件未查明则保留疑似。排除某条规则的嫌疑不代表可排除其他规则的独立问题。

## 隐私主动同意（privacy-consent）

- 用隐私文案/控件名/绑定建立关联，不能仅凭文件里出现“隐私”就把全部 Checkbox 算作隐私控件。
- 检查 Checkbox.select 和 Toggle.isOn，追踪所属组件内的状态初值。其他组件同名状态不应混入。
- 初值 true 需核实首次展示前是否被生命周期覆盖；初值 false 也可能被生命周期自动改为 true。直接用户回调里的赋值不是默认同意的证据。
- 恢复保存状态、动态初始化和间接调用必须记录未知或继续追踪，不把状态名当作证据。
- “登录/注册即代表或视为同意”等 UI 文案需与实际交互一起核实；源码日志中的相同文本不属于 UI 证据。
- 隐私弹窗无拒绝选项、非主动同意由 Agent 沿 reviewTargets 复核按钮、取消与退出路径、状态写入。自动脚本仅提供入口，不宣称完整覆盖这两项。

每个确认结论至少包含：规则、入口/组件、证据位置、必要的资源/状态链以及适用场景。缺少入口证明或关键动态数据时保持“疑似风险/源码无法确认”。
