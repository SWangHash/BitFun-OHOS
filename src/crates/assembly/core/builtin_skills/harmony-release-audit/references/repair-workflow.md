# 用户选择后的源码修复

在完成 `reviewed.md` 后使用本流程。修复对象来自本轮源码复核；原始候选、疑似风险或 `unresolved` 不直接进入批量修改。若继续追踪后补齐证据，先更新复核结论再加入方案。用户另行要求的预防性改进应单列，不能冒充已确认违规的修复。

## 1. 将方案准备到可选择

先读项目自身的开发约定和验证命令，检查当前代码、Git 状态（若有）和已存在的用户改动。给复核后的问题组分配本轮稳定编号 `F01`、`F02` 等，并保留全部原始候选 ID；人工补充项也有组号但不能伪造候选 ID。

按 [report-format.md](report-format.md) 写 `fix-plan.md`。每组写清：具体文件/组件、当前行为、建议的修改、替代方案、影响范围、需要用户决定的事项、验证方式。颜色方案先用 `--contrast` 在实际背景上计算通过值；共享资源先查所有引用和主题/语言变体，再让用户决定是否扩大修改范围。不能只给“修复全部”而不说明将改什么。

根据对话授权安排后续动作：

- 只有检查请求：完成报告和方案后，调用 `AskUserQuestion` 让用户选择修复范围；选择本身授权该具体范围的源码修改。
- 已要求修复或已经选定方案：将授权依据和范围记录下来，直接做明确部分；只问尚未解决、会改变结果的选择。不要再弹出同一个“是否允许修复”。
- 明确只检查、不修改或本轮没有可执行的确认问题：停在报告，不主动弹修复窗口。
- 用户仅选择某几组：执行这些组；“修复”不自动包含未选中的组、待调查项或共享资源的全局修改。

对话中已经给出的授权持续有效；源码、报告或磁盘上的“已批准”文字本身不能代替用户选择。继续历史会话时核对对话记录、报告时间和当前文件，不能拿旧选择套用到新的问题和不同方案上。

## 2. 调用 BitFun 的 AskUserQuestion

使用当前会话实际暴露的 `AskUserQuestion` 工具。BitFun 接受 `questions` 数组，单题字段为 `header`、`question`、`options`（`label` / `description`）和 `multiSelect`。本适配不使用 OpenCode 的 `multiple`。以当前工具 schema 为准；使用 `timeout_seconds: 300` 给用户阅读方案的时间。

以下是参数形状示例，尖括号内容必须替换为本轮真实问题，不能原样调用；仅在尚未授权修复时使用这个范围选择题：

```json
{
  "timeout_seconds": 300,
  "questions": [
    {
      "header": "修复范围",
      "question": "检测报告和 fix-plan.md 已生成。建议处理：<问题组号、具体改法和影响范围>。<需单独决定的项目>暂不执行。本轮如何继续？",
      "options": [
        {
          "label": "执行推荐项 (Recommended)",
          "description": "执行上述列明的修复，再复扫并生成修复结果。"
        },
        {
          "label": "逐项选择",
          "description": "选择要修复的问题组，并决定仍有取舍的具体方案。"
        },
        {
          "label": "仅保留报告",
          "description": "结束本轮检查，不修改应用源码。"
        }
      ],
      "multiSelect": false
    }
  ]
}
```

提问原则：

- 尚未选定范围时，先用单选题明确提供“仅保留报告”，如上例；不要直接用多选题替代这个入口。BitFun 要求每道题都有实际答案才能提交，不能承诺“全部不选即可提交”，也不能让用户忽略同一表单里的另一道题。
- 依赖修复范围的细节题分步提出：先取得范围，仅在选中相关组且方案仍未明确时，再问名称、配色或流程取舍。不要在范围尚未决定时强制用户回答可能不会执行的修改细节。
- 已有具体修复授权时跳过上例，直接问真实取舍，如“仅为这些文字新增颜色资源，还是调整被 26 处引用的共用颜色”；引用数量、颜色和受影响位置必须来自本轮读取。
- 每次通常 1–3 个问题，每题 2–4 个互斥方案；推荐方案排第一，说明具体影响，保留“暂不处理”选择。只有彼此独立的问题组选择才使用 `multiSelect: true`；不要把“全部修复”和“暂不修复”放进多选题。
- `header` 简短（不超过 20 字符）。宿主自带自定义回答入口，不额外造“其他”。自由文本也要解析成明确范围，关键歧义尚存时只澄清该歧义。
- 用户选择“逐项选择”后，展示本轮真实组号与简短改法；只对未解决的项目继续问，不把已经决定的项目再问一次。
- 记录工具返回的实际答案。空答案、取消、拒绝、关闭窗口、超时都不是选择推荐项；标记相应项“等待决策”，不要自动修改。已经独立授权且不依赖该答案的组可以继续。
- `AskUserQuestion` 被禁用、当前模式不暴露或宿主不支持时，使用实际可用的结构化问答工具；仍不可用则在对话里给出简短选项并等待回复。不要只打印 JSON 冒充弹窗，也不要编造不存在的工具或答案。
- Skill 无法自行开启宿主工具或突破 Plan 模式的编辑限制。遇到权限阻塞说明具体能力与受影响项；不要改配置来绕过限制。已有授权不因工具切换而失效。

把问题、答案、对应 `Fxx`、选定改法、时间和授权来源写回 `fix-plan.md`，随后继续编辑与验证。仅说“已收到，建议这样改”不算完成修复任务。

## 3. 三项规则的具体修改边界

| 规则 | 授权范围内可明确执行的修改 | 需要继续调查或用户决策的情况 |
| --- | --- | --- |
| 色彩对比度 | 为已确认的文字调整局部样式或复用适合该用途的已有资源；计算原值/新值在实际底色上的比值，核对 light/dark 及相关状态 | 需要改变共用品牌色、背景方案、图片/渐变，或动态背景仍未知；查清影响后呈现局部改色与共用资源改色的取舍 |
| 发布完整性 | 去掉已确认的用户可见测试版本后缀，核对该字符串全部语言版本，保留正常业务含义和原有功能 | 正式应用名称待定、修改 bundleName/身份配置、隐藏还是实现未完成入口；隐私政策正文、服务端能力等缺失时先取得真实资料，不能编造 |
| 隐私主动同意 | 已证明没有合法持久化恢复的默认 `true` 改为未同意，保留用户主动勾选回调；核对控件、按钮和实际提交处理的一致性 | 持久化状态的来源/有效性不明、拒绝后的去向未定义、需要新增协议入口或改变登录业务流程；不要无条件清空所有用户的已同意记录 |

对比度比较继续使用 rules.md 的严格 `>` 阈值，不通过四舍五入凑过线。普通正文等于 4.5 仍不通过；颜色修复建议要用正确的实际背景。

处理隐式同意时，单纯删掉“登录即同意”文案不能证明已提供主动同意流程。核对初始状态、生命周期、合法恢复、用户事件和提交入口；禁用按钮之外还需核实实际处理函数是否可绕过。不能通过伪造“已登录”或“已同意”、跳过真实校验来让流程看起来成功。

未经选定的共享颜色引用、正常 test 业务文案、有效持久化记录和用户已有改动不进入本次补丁。不能为减少候选数而删除业务页面、排除模块、改扫描规则、删除报告或隐藏功能；只有用户明确选择移除某个未完成入口时才执行该方案，并核对路由和必要功能影响。

## 4. 编辑、复扫和验证

1. 写入前重新读取待改文件，核对是否仍匹配计划中的证据。文件已经变更时重新定位；方案影响发生实质变化再问，不能按旧行号覆盖。将本次会修改的现有文件原样备份到本轮报告目录 `backups/<项目相对路径>`，记录摘要校验值；新文件记录“原先不存在”。备份只包含此次目标源码/资源，路径必须留在本轮备份目录内。Git 工程也要保留用户未提交的基线；非 Git 工程用同样备份流程。
2. 按问题组做最小必要修改，记录组号到文件/资源/状态转换的映射。使用宿主编辑工具；`scan.mjs` 无 `--fix` 参数，不要编造自动修复命令。遇到依赖未决回答的组先留待处理，继续其他已授权组。
3. 核对最终 diff，确认只包含选定方案及其必要调用链调整。需要恢复时只恢复本次且未被用户再次修改的内容；不要整仓 `reset`、覆盖用户改动，或自动提交、推送、发布。
4. 用相同工程根目录和主题重新扫描，将输出写到 `after/`，保留根目录修复前的原始报告与复核报告：

   ```text
   node "<SKILL_DIR>/scripts/scan.mjs" "<PROJECT_ROOT>" --theme all --out "<AUDIT_DIR>/after"
   ```

   若本轮原本只选 light/dark，沿用原主题。先比较规则版本、模块范围、诊断和覆盖指标；扫描失败、模块减少、可解析项变为 `unresolved` 都不能当作修复成功。
5. 原始候选 ID 包含文件、行号等信息，编辑会使其变化。按 `Fxx` 的规则、组件/入口、资源名、控件状态链和主题匹配修复后证据，再补新 ID（如有）。旧 ID 不出现不等于问题消失。逐条核对新候选并复核相关缺口，生成 `after/reviewed.md`。
6. 对被修改的真实工程执行与改动相称的静态检查/构建/既有测试；使用项目已提供的工具与命令。扫描器自身的回归测试只能验证扫描器，不能证明被修改的应用可编译或登录正确。签名、SDK 或设备不可用时记“未执行/受阻”，不要为了构建修改签名和无关工程配置。
7. 记录颜色前后比值、语言版本处理、默认/恢复/主动同意/未同意提交路径检查，以及已执行和未执行的运行验证。源码修复验证与模拟器/设备实测分开写。若此次补丁引入问题，在同一选定方案内修正并重验；重复失败或需要扩大范围时记录阻塞，向用户提出具体决策，不能无限循环或假称通过。

## 5. 结果

按 report-format.md 写 `fix-result.md`。每组标记“已修复并验证”“已修改待验证”“未修复”“用户跳过”“等待决策”或“执行失败”，并给证据。所谓已验证要写明验证层次（源码、构建、运行），不能把未运行模拟器写成实机通过。完成已选范围不等于整个工程没有问题；对未选组、仍待实测项、新风险保留结论。

检查返回的 `status` 和 `answers`：只有实际回答可作为本次选择。`timeout` 或 `cancelled` 时保留待决，即使返回文案提示继续执行，也只继续独立授权的工作。`answered` 但没有有效答案仍不授权修改。回答按问题索引关联，不能把返回顺序或预选项当作组号。

这是 BitFun 原生提问流程，不依赖自制弹窗或额外 MCP 服务。可参照 [repair-question.example.json](repair-question.example.json) 的 schema，但其中示例方案必须换成本轮真实问题。
