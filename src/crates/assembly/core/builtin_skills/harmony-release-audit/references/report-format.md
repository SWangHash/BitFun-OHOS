# 源码预检报告

标明工程、规则版本、原始报告 `generatedAt`、phone 范围、检查的主题、扫描完成情况；不要推断已连接虚拟机或已构建发布包。开头用简短摘要给出确认问题、待核实风险、主要覆盖缺口和优先处理项。

检查项用中文名称呈现，需要机器标识时只使用 `color-contrast`、`release-readiness`、`privacy-consent`。所有新报告、修复计划和修复结果均不引用外部审核规则序号；历史报告按当前源码证据重新关联，不能原样转抄旧标识。

摘要使用可比的覆盖指标：`textNodes` 是文字节点数，`contrastStates` 是节点×主题数，`evaluatedContrastStates` 是可计算状态数，`inheritedBackgroundStates` 是其中采用父背景的状态数。不要把两种主题的同一节点说成两个独立页面。

模块范围来自 `moduleScope`；说明纳入的入口及依赖、排除模块的理由，并处理全部 `scopeNotes`。依赖声明与设备声明冲突时说明是否已扫描；归档或缺失依赖仍是缺口。`diagnostics` 为零只表示没有记录到配置解析等诊断，不表示检查了全部代码或全部审核规则。

脚本的 `report.json/report.md` 是原始事实与候选；经 Agent 复核后的 `reviewed.md` 包括：

1. **确认问题**：规则、位置、入口或显示路径、证据链、确认理由和具体建议。
2. **疑似风险**：同样字段，说明尚缺什么证据。
3. **排除的候选**：给出候选 ID 和排除原因，避免下次重复误报。
4. **源码无法确认**：逐文件说明未完成的动态/跨组件/图片背景等检查；候选和未解析列表没有全部读完时明确写出未处理范围。

颜色证据包括主题、前景、背景及其定义路径、比值、文字角色与角色依据。按 rules.md 对同类用途统一判定，不能一处以“交易重要”确认、另一处又把普通状态文字视为可能的标题。每条配色建议记录 `--contrast` 的前景、实际背景、计算比值和适用阈值；调整背景时一并说明。状态证据包括控件、声明初值、覆盖赋值、触发路径。测试标识证据包括原文、全部语言资源、使用组件及发布可达性。相同位置/比值的 light、dark 候选可合并为一项并列出主题。

统计口径：原始候选数、合并后的问题组数、人工补充风险数分别计数。每个 `findings.id` 恰好归入确认、疑似、排除或尚未复核中的一类；合并时保留全部候选 ID。`reviewTargets` 和 `unresolved` 不冒充候选 ID，发现新问题标为“人工补充”并给源码证据。不能把“不是隐私默认同意”写成对一个未完成菜单的全面排除。

不得因小字号自动认定正文，不得用舍入后的比值比较阈值，不得从“未发现隐私弹窗”直接推导“默认同意”，不得把未使用资源词语认定为正式 UI。原始配置的签名材料和与风险无关的凭据不要写入报告。

示例：

```text
规则：色彩对比度
候选 ID：来自 report.json
结论：疑似风险
位置：entry/src/main/ets/pages/Example.ets:42
主题：light、dark
证据：前景白色；父 Column 背景来自 color.json:9；比值 4.213283...
待确认：该文字在页面上属于正文还是标题；入口是否在正式版本开放
建议：确认正文身份后提高对比度；建议的新颜色必须重新计算验证
```

没有确认问题时写“本次已完成的三项源码预检未确认风险”，并保留疑似风险、诊断和覆盖缺口。存在未处理候选时明确标为部分复核，不能写全量完成。最终结论不等于商店审核结果，不使用“硬性拒绝项”等无正式审核依据的措辞。

完整工程检查总是将本次复核写入同目录 `reviewed.md`，并核对它引用的版本与生成时间和原始报告一致。聊天回复只需给结论、优先项和这三个文件的路径，不要求用户逐项报出规则或缺陷位置。

## 修复方案 fix-plan.md

在展示修复选择或执行已授权修复前写出。它应是能让用户决定具体改法的方案，不是只有“待修复”的问题清单。

- 本轮工程、规则版本、原始 `generatedAt`、修复前 `reviewed.md` 路径，以及用户请求的模式（只检查/待选择/已授权修复）。
- 每个问题组的 `Fxx`、原始候选 ID（人工补充注明无 ID）、确认依据、位置/入口、当前行为、推荐修改和替代方案。
- 精确的拟改文件、资源、状态转换及影响范围。共用资源列引用数与所及场景，颜色方案列前后输入颜色对和实算比值，不能只写“加深颜色”。
- 需要用户回答的具体取舍；已回答的记录问句、实际选项或自由文本、时间、来源及所授权的 `Fxx` 和方案。以本轮对话/工具返回为准，不自行填“默认同意”。
- 每组状态（待选择/已选定/用户跳过/待补证据），以及计划执行的源码检查、工程检查与需运行验证的内容。
- 修改前备份的相对路径与文件摘要值；新文件记录原先不存在。用户原有未提交改动的存在与涉及范围，不把它们算成本次修复。

若方案变化，记录变化原因；不再适用的选择不能自动授权新增范围。

## 修复后报告与 fix-result.md

保留根目录 `report.json`、`report.md`、`reviewed.md` 作为修复前基线；修复后扫描写到 `after/report.json`、`after/report.md`，Agent 按本文件同一复核口径写 `after/reviewed.md`。`fix-result.md` 连接前后证据：

| 字段 | 要求 |
| --- | --- |
| 修复依据 | 前后 `generatedAt`、规则版本、主题和范围；用户实际选择及对应方案 |
| 逐组结果 | `Fxx`、规则、原始候选 ID、新候选 ID（若有）、实际修改文件与最终行号 |
| 修复证据 | 颜色前后比值和实际背景；处理的全部语言版本；隐私初始状态、恢复来源和用户操作/提交路径 |
| 验证 | 执行命令、结果和验证层次；构建/设备等未执行项及原因；不能把扫描器单元测试当作应用测试 |
| 未完成项 | 未选组、待决项、失败、未修复或已修改待验证项目，逐项注明原因 |
| 前后覆盖 | 模块范围、诊断和 coverage/unresolved 的变化；候选转为未解析不是修复成功 |
| 回退依据 | 本轮目标文件备份/摘要和新建文件清单，说明恢复时需先核对当前内容 |

每组只给一个执行状态：“已修复并验证”“已修改待验证”“未修复”“用户跳过”“等待决策”或“执行失败”。状态与源码问题分类是两个维度：用户跳过的确认问题仍是确认问题。统计所选组数、成功组数、待验证/失败/待决/跳过数量，并另列本轮新发现的风险，避免把候选条数和问题组数混用。

颜色组合变合格但构建未验证，应说明源码证据已验证和构建未执行；不要将其描述成完整应用验证通过。复扫后 ID 变化按组件/资源/状态语义对应；不能仅用原 ID 消失判为已修复。最终回复给修改摘要、剩余风险和 `fix-result.md`、`after/reviewed.md` 路径。
